# Running a rating round

1. **Pick and screen:** `python3 jevaluate/scripts/screen_list.py <list README> --known-yes <repo that calls Jev> --known-no <repo that doesn't>`; it stops if either control is misclassified. Quote counts from its output. Never classify repos with GitHub code search.
2. **Size before spending:** for each project: `python3 jevaluate/scripts/coverage_manifest.py <owner/repo> <dir>` (add `--commit <sha>` to pin one), then `python3 jevaluate/scripts/step.py estimate <dir>/manifest.md`. Large data files are sampled by content; question catalogues stay whole. For a large repo, shallow-clone (`git clone --depth 1 --filter=blob:limit=300k <url>`) and read locally. Agree the total, and each scoped rating, with the owner before dispatch. For an estimate above 200k, write `approved_cost.json` (`{"approved": <n>}`) in the rating's folder yourself; `step.py` refuses to start without it.
3. **Brief raters:** give each `rater-brief.md` with PROJECT, SLUG, ROUND_DIR, PREV, VIA, SCOPE, RUBRIC (the date in `rubric.md`'s title), RATER (the rater's model ID: `claude-sonnet-5-5` in Claude Code, `gpt-6-sol` in Codex) and JEVALUATE (the absolute path to the `jevaluate/` folder) filled, so no rater opens the rubric. Raters read `SKILL.md` and `read.md`; `step.py` serves the rubric one phase at a time, and past ratings only after the comparison step. Raters write only their own folder and never run `library.py add`, commit or push. Dispatch several in parallel; drop the count if calls hit rate limits.
4. **Scan each transcript before logging it:** `python3 jevaluate-harness/scan_transcripts.py <rating.md> <transcript>` per rater (the transcript is the `output_file` in its launch result), in its own command, never chained to `add`. A flag sends the rating back; a rater that writes `approved_cost.json` or `routing_revised.json` is flagged. The scan is a backstop: globs and indirect reads can slip past it. Also read the transcript for two things the scan misses: a fact, score or verdict changed after `step.py full` showed the previous rating, and a served section piped through `head` that lost text. Either sends the project to a fresh rater; the first rater can't un-see what it read.
5. **Log one at a time:** once its transcript is clean, `python3 jevaluate/scripts/library.py add <rating> --evidence <dir> --link-docs` for one rating at a time. `add` runs `check`, which refuses a rating whose calls-Jev line doesn't cite a real call, whose F11 or F13 answers don't fit its listed stakes, or whose step log is missing or out of order. Send a refused rating back to its rater with the refusal text; never hand-fix it. A routing change after the facts is refused until you check it and write `routing_revised.json` (reason and time) in its folder.
6. **Adjudicate:** send any verdict move of 2 or more points, and any rubric line a rater called ambiguous, to a fresh reviewer given only the facts. When two raters disagree on what the code does, build a blind packet per fact (`scripts/dispute_packet.py <rating A> <rating B> <fact> <evidence dir> --seed N`) and give a fresh reviewer only that packet. The controller has read both ratings, so it never settles these itself. Before sending a ruling back to a rater, apply it to a copy of the rating and run `library.py check` on the copy; a ruling `check` refuses is a rule change (step 7), not a re-rate. When a disagreement is settled, record which rating the ratings list shows with `library.py review <slug> --use <claude|codex>`, where the slug is the project's page name, such as `altryne__jevify`; the next export shows it.
   - **Two raters on one project** (a second model, or a re-rate): first check every fact they split on against the evidence yourself and settle the ones the code answers, with file:line. Only rule readings, where both raters saw the same code and read the rule differently, go to the owner: one page of plain questions, each with the project in a sentence, every number it needs, two readings to pick from, and no rater names, answered before any model answer is shown.
7. **Changing a rule mid-round:** before ruling on a threshold or a check, run the proposed rule against the real manifests or ratings on disk and show which files or answers change. Log the ruling with its cost if wrong.
8. **Final gate:** a fresh reviewer, given only the ratings and the ledger, checks the round before publishing: refused or flagged ratings resolved, adjudications logged, no private context. Log it as `final-gate`.
9. **Record:** tokens per rater from its task notification; headless calls by their `usage`. Findings for the next rubric change go to `jevaluate/rubric-tuning-log.md` (create it if missing: one section per round, with the date, the rubric version, and each finding with the ratings that show it).
